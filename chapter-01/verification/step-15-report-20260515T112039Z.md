## 10. Surprises and notes

### 10.1 Stripe key prefix gotcha

The first two keys the user pasted were `mk_*` (Stripe Meter Events authentication), not the standard `sk_test_*` secret key. The `mk_` prefix is for usage-based billing and won't authenticate Checkout / subscription endpoints. Stripe rejected each with `Invalid API Key provided`. Easy mistake to make in the Stripe Dashboard if you click into the wrong section. The launcher checklist now points at `https://dashboard.stripe.com/test/apikeys` specifically.

### 10.2 Vercel preview deployment protection

The clean answer (preview environment) was unblocked because Vercel gates all preview deployments behind 401 by default. Stripe webhooks cannot authenticate, so the preview environment is unusable for any webhook-based test until either (a) deployment protection is disabled, or (b) a "Protection Bypass for Automation" token is added as a query-param-token on the webhook URL. Both are project-level Vercel settings; neither was wired up. Step 15 worked around this with a temporary prod-env swap. Chapter 10 should pick this up.

### 10.3 URL fragment in chat clients

Stripe Checkout URLs include a long `#fragment` that carries form state. Some chat clients truncate or mangle the fragment on click. The workaround that worked: a local HTML launcher (`/tmp/step15-launch.html`) with the URL as a proper `<a href>`. The user opened the launcher in their default browser via `open /tmp/step15-launch.html`. This is also useful for the regression checklist.

### 10.4 Foundation page session-restore on success redirect

When Stripe redirects to `success_url=https://app.quantumbranding.ai/foundation?upgrade=success` and the browser's localStorage session has expired or is absent, the foundation page bounces to signal-scan (the auth gate). The user hit this. It is a UI gap rather than a payment gap; the webhook still fired, the tier still flipped. The fix is to teach foundation.html to recognize `?upgrade=success` and, if the session is stale, prompt for re-sign-in with a banner rather than silently redirecting to signal-scan. Documented for a follow-up patch.

### 10.5 Stripe minted a new customer on resubscribe

After `DELETE /v1/subscriptions`, the customer object stayed in Stripe but had no active subscription. The next Checkout session opened with `customer_email` only (not `customer` ID), so Stripe minted a fresh customer (`cus_UWMQTuqZ89wxCe`) instead of reusing the old one (`cus_UWMMO6fv2b7u3x`). The webhook handler correctly overwrote `profiles.stripe_customer_id` with the new ID, so audit trails downstream are coherent.

This is acceptable for Chapter 1. A future hardening would pass `customer: <cus_id>` explicitly in `/api/stripe/checkout` when `profiles.stripe_customer_id` is set, so the same customer object is reused across cancel/resub cycles. Improves Stripe-side reporting hygiene but doesn't affect tier-flip correctness.

### 10.6 `tier_started_at` survives downgrade

The webhook handler's `customer.subscription.deleted` branch only sets `tier='free'` and `subscription_status='canceled'`. It does NOT clear `tier_started_at`. The audit trail of "when did this user first reach starter" is preserved across cancel/resub cycles. Resub overwrites it with the fresh timestamp (per `checkout.session.completed` handler logic), so the value always reflects the LATEST starter activation, not the first one.

### 10.7 Idempotency check pattern is reusable

The HMAC-SHA256 manual signing in `/tmp/step15-replay.mjs` is a generic pattern for testing the webhook handler in isolation. Any Stripe event fetched from `/v1/events/<id>` can be replayed with a fresh signature to exercise dedup, error handling, or new event-type handlers without touching production data. Saved as part of the manual checklist.
