## 2. State machine

`computeFoundationState({ qbp, artifacts, foundationLockedAt, tier })` returns one of four primary buckets. Each bucket has its own renderer.

| Bucket | Trigger | Render |
| --- | --- | --- |
| `cold` | empty QBP + no lock | hero + 3 free-tier exercise cards in "Begin" state + 2 paid-tier teasers |
| `in-progress` | partial QBP, no lock | hero + segmented progress bar (N of 3) + exercises in mixed states |
| `lock-ready` | all 3 free-tier exercises complete, no lock | hero with prominent "Lock the foundation" CTA + completed exercises list |
| `locked` | `foundation_locked_at` present | three sub-states (see below) |

### Locked sub-states

The locked bucket branches on artifact status and tier:

| Sub-state | Condition | Render |
| --- | --- | --- |
| `locked-generating` | any artifact in `queued`/`generating` | hero with "Synthesis in motion" eyebrow + queue panel listing the four Phase 01 agents + per-agent status (delivered ✓ / generating / queued) |
| `locked-delivered-free` | all artifacts settled, tier=free | hero + 4-tile grid (Soul Map open + 3 locked with paywall trigger) + upgrade banner |
| `locked-delivered-starter` | all artifacts settled, tier∈starter/pro/agency/atelier | hero + 4-tile grid (all 4 open) + next-step banner ("Phase 02 opens next.") |

A "settled" artifact = status is `delivered` or `failed`. The renderer treats the four canonical agents (`soul_map_synthesizer`, `sensescape_synthesizer`, `visual_dna_synthesizer`, `war_table_synthesizer`) as the Phase 01 set.

## 3. Lock CTA flow

The lock-ready bucket renders a prominent `createLockFoundationCta` button. The CTA flow:

1. User clicks "Lock the foundation."
2. Confirmation modal opens with copy: *"Locking the foundation runs the four Phase 01 agents. Brand Soul Map, Sensescape, Visual DNA, War Table. Each artifact lands within a few minutes."* + "Lock it" / "Not yet" buttons.
3. On confirm, `foundation.html` calls `POST /api/foundation/lock` with `Authorization: Bearer <token>`.
4. On 200 response, the page re-fetches `/api/qbp` and `/api/artifacts`, then re-routes via `computeFoundationState`. Because `foundation_locked_at` is now set, the user lands on `locked-generating`.
5. `startArtifactPolling` begins immediately. Toast banner: *"Synthesis dispatched."*
6. On non-200, the modal stays open with the server error message inline.

The `createLockFoundationCta` factory carries the v3.3 two-layer pill treatment plus an `is-disabled` state used when the user lacks the three required exercises.

## 4. Polling implementation

`startArtifactPolling({ token, onUpdate, onStuck })` is exported from `js/qb-foundation.js` and consumed by `foundation.html` only when the bucket is `locked-generating`.

Parameters:

| Parameter | Value | Source |
| --- | --- | --- |
| `POLL_INTERVAL_MS` | 10 000 ms | spec §9 |
| `POLL_MAX_MS` | 300 000 ms (5 min) | spec §9 |
| Hidden-tab interval | 1 000 ms (re-arm without API call) | local optimization |

Lifecycle:

- Hits `GET /api/artifacts` every 10 s, parses the response, computes "all four agents settled?"
- If `document.hidden` is true, the timer rearms after 1 s without making the API call (cheap polling, observable wake on visibility return).
- On every tick, fires `onUpdate(artifacts)` so the page can re-render the queue panel with per-agent progress.
- When all four settle, fires `onUpdate` one last time, then stops itself. The page re-renders into `locked-delivered-*`.
- After 5 min wall time with not-all-settled, fires `onStuck()` and stops. The page surfaces a "Synthesis is slower than expected. Refresh in a few minutes." toast and keeps the queue panel visible.
- `beforeunload` cleanup: the page calls `stop()` on the returned handle so the timer is GC-safe.

The polling handle is also stopped if the page navigates away or if the user manually re-renders (e.g. on tab focus → if state has moved to `locked-delivered-*`, polling is no longer needed).

## 7. Surprises and notes

### 7.1 Test user lives in `locked-delivered` permanently

The canonical test user (`3a92ffba-…`) already has `foundation_locked_at` set from the step-6 dispatch session. As a result, the smoke can only verify the `locked-delivered-*` sub-states. Verifying `cold`, `in-progress`, `lock-ready`, and `locked-generating` against production data would require a fresh user. The gallery harness (`tests/foundation.gallery.html`) covers all seven states with synthetic fixtures. That harness is the visual SOT for the four pre-lock buckets.

### 7.2 QBP key presence ≠ exercise completion in production

The test user's QBP has only `archetypePrimary='The Rebel'` set, yet `foundation_locked_at` is populated. This is because the step-6 dispatch ran the agents directly without forcing the user through the Brand Soul Map / Sensescape exercises. The renderer correctly prioritizes `hasLock` over QBP key presence: once `foundation_locked_at` is set, the user is in the `locked` bucket regardless of what the QBP looks like.

### 7.3 `_supabase/auth/v1/verify` requires email in the body

The previous step's smoke pattern (POST to `/auth/v1/verify` with `token` + `type` only) returned `validation_failed: Only an email address or phone number should be provided on verify` on this Supabase project version. Switched to following the `action_link` returned from `generate_link` with `redirect: 'manual'` and extracting `access_token` from the redirect Location fragment. This is the same flow the auth callback page uses; it works against the current Supabase auth contract without needing the email in the verify body.

### 7.4 The paid-tier exercises are visible from cold start

The `cold` state shows two teasers for Visual DNA and War Table beneath the three free-tier exercise cards. Each teaser carries the locked-tile treatment (rose-deep status pill reading "Starter") and clicks to the paywall. This is per spec. The user sees the system's structure before subscribing.

### 7.5 Locked sub-state computation requires server-side `locked` flag

The renderer never re-derives lock state client-side from `tier` + `agent_slug`. It trusts the per-row `locked` flag the artifact API attaches based on the tier-gating module. This keeps the source of truth on the server and prevents drift between the renderer's lock logic and the API enforcement. Confirmed in the smoke: free-tier response has 6 of 9 rows locked; starter-tier response has 0 of 9 rows locked.

### 7.6 Three wrapper classes have no CSS

`qb-foundation-exercises`, `qb-foundation-tiles`, and `qb-foundation-upgrade-banner__copy` are wrapper elements with no own styles. Only their children carry rules. Intentional: the wrappers are pure semantic anchors for the inner grids and flex containers. The cross-grep confirms only these three are JS-only; every other class in the renderer has a matching CSS rule.

### 7.7 Polling pauses but does not pause `onUpdate`

When `document.hidden` is true, the poller does not fetch but rearms after 1 s. When the tab returns to visibility, the next tick runs immediately at the regular 10 s cadence. This avoids burning the API quota for an inactive tab without making the user wait for a fresh poll after a long idle. The 1 s tick is a cheap setTimeout, not a fetch.

### 7.8 The retired files are still in the repo

`dashboard.html`, `qb-branidos-hub.html`, `journey-guide.html` are not deleted. They are routed away from production via vercel.json but kept in the git tree with deprecation headers. This protects the historical record (anyone reading the new foundation markup can diff against the prior chassis) at the cost of three dead files. A later cleanup can drop them once Chapter 1 ships and the prior versions are not referenced in any open PRs or discussions.
