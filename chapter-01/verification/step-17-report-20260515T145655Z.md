### 3.3 Lock attempt → 2 critical bugs surfaced

**Bug A: foundation.html POSTs to wrong path.**
`foundation.html:96` calls `/api/foundation/lock` but the endpoint file is `api/lock-foundation.js`, resolved by Vercel filesystem routing at `/api/lock-foundation`. No vercel.json rewrite bridges the two. Production lock CTA was silently 404ing.

**Bug B: lock endpoint REQUIRED_TOOLS mismatch.**
`api/lock-foundation.js:40` required all 4 exercises (`soul-map`, `sensescape`, `visual-dna`, `war-table`) but Visual DNA + War Table are paid-tier exercises that free users never complete. Per spec §15.1 and the Foundation UI's `REQUIRED_FREE_SLUGS` (`['archetype-compass','brand-soul-map','sensescape']`), free tier should lock after the three free-tier exercises.

Reproduction transcript:
```

POST /api/lock-foundation (correct path) → 409 {"ok":false,"error":"Phase 01 incomplete","missing":["visual-dna","war-table"]}
```

**Fix applied in PR #57 (`b295848`):**
- `foundation.html:96` → POST to `/api/lock-foundation`
- `api/lock-foundation.js` → `REQUIRED_TOOLS = ['archetype-compass', 'soul-map', 'sensescape']`

Severity: CRITICAL on both. Either bug alone would break the user path. Why these weren't surfaced earlier: every prior step that interacted with `lock-foundation` did so via direct admin patches (steps 6, 12, 15) rather than the user-driven path. Step 17 is the first integration test that walked the real path.

### 6.4 Spec 10.12 · regenerate-while-generating
Two `POST /api/artifacts/<soul_map>/regenerate` calls fired ~1s apart:
```
[A] HTTP 200  {"new_artifact_id":"...","version":2,"status":"delivered"}
[B] HTTP 409  {"error":"previous_run_in_flight","current_status":"generating"}
```

B was correctly rejected because A's row had `status=generating` when B's check ran. After A delivered, B would have been able to start a v3. The dispatcher's `findOrCreateArtifact` reuses any in-flight row, so the 409 is the right gate at the regenerate-endpoint layer.

## 8. Surprises and notes

### 8.1 The single biggest surprise: production lock was broken

The lock CTA on `/foundation` has been silently 404ing since step 12 shipped. No prior step exercised the user-driven lock path (steps 6, 12, 15 all bypassed the API via direct admin patches or by injecting the lock state in the test database). Step 17, the first true integration test, surfaced it within the first 10 minutes of the synthetic walkthrough. This is exactly the kind of bug the step exists to catch.

If step 17 had been skipped or run in API-only mode without the lock attempt, Chapter 1 would have shipped with the user path's most critical CTA broken. The fix is a 1-line change in foundation.html plus a 1-line change in REQUIRED_TOOLS. Total fix surface: 2 files, 10 net lines added (counting the new comment).

### 8.2 Edge timeouts on lock + regenerate are a real Chapter 10 design problem

Vercel Edge functions have ~25s budgets. `/api/lock-foundation` synchronously dispatches 4 agents that each call Claude. Even though the agents run in parallel via `Promise.all` and typically finish in ~5s of wall-clock, the variance can push past 25s, especially when the network jitters. Same for `/api/artifacts/<id>/regenerate` which runs one agent synchronously.

The right answer is async dispatch with a polling state endpoint (the polling already exists in `js/qb-foundation.js`). The lock endpoint should:
1. Verify auth + completion
2. PATCH the lock + send the lock email
3. Fire dispatch in the background (or enqueue to a worker)
4. Return immediately with `{ ok: true, lockedAt, dispatch: 'queued' }`

The client already polls for artifact state after lock. Decoupling the lock-response from the dispatch-completion would eliminate the timeout class entirely. This is significant Chapter 2 / Chapter 10 work, not a Chapter 1 fix.

### 8.3 The synthetic webhook approach is robust

Signing a fake `checkout.session.completed` event with the live webhook secret + `tier_intent` in metadata produces a real tier flip without any Stripe-side state. This pattern is reusable for future testing whenever the user path doesn't need actual Stripe involvement. Worth committing the script to `tests/` if Chapter 10 needs more webhook-driven regression coverage.

### 8.4 Two slug conventions live in tool_completions

The Foundation page's UI registry calls Brand Soul Map by the slug `brand-soul-map` but the exercise page (`brand-soul-map.html:4937`) writes `soul-map` to tool_completions. The lock endpoint reads `soul-map`. The Foundation UI's lock-ready check looks at QBP key presence (`brandEssence`, `manifesto`), not the slug, so the convention drift never triggers a UI bug. But anyone debugging tool_completions sees `soul-map` AND `brand-soul-map` (the seed script wrote both to be safe). Logged as a Low/cosmetic finding.

### 8.5 API-only mode misses the visual layer entirely

Every renderer was already verified via gallery harnesses in steps 8-13 against synthetic fixtures. The integration question that step 17 was supposed to answer is: do those renderers behave correctly against REAL data from REAL APIs at REAL viewport sizes? The API contracts pass cleanly, but visual rendering on mobile/desktop is unverified for this end-to-end run. Step 18 sign-off SHOULD include a manual browser walk-through of the same surfaces against the test user (which is left in place specifically for step 18 to consume).

### 8.6 Test user is preserved for step 18

Per spec 17.10, the test user profile is left in place with `tier=free` (cleanup-reset). All 7 artifacts remain in the database. A step 18 manual walkthrough can sign in as this user via magic link and verify the visual surfaces against real data without needing to seed anything.

Magic link generation: `POST {SUPABASE_URL}/auth/v1/admin/generate_link` with `{type:'magiclink',email:'nizzar.ben+c1qa-20260515t144543@gmail.com'}` returns an `action_link` that the user can open in any browser to assume the test user's session.
