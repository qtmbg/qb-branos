## 4. Integration points

### 4.1 Foundation lock

`api/lock-foundation.js` after a successful `PATCH /profiles` write (and before agent dispatch):

```js
if (RESEND_API_KEY && profile.email) {
  await sendLockEmail({ email: profile.email, firstName: profile.first_name || '' });
}
```

`sendLockEmail` calls the new `sendEmail` helper with `EMAIL_TEMPLATES.FOUNDATION_LOCKED`. Result is not blocking. Idempotency is already handled at the lock layer: if the profile already has `foundation_locked_at`, the endpoint short-circuits at the top of the handler with `alreadyLocked: true` before reaching the email send. So re-running the lock endpoint cannot re-fire the email.

### 4.2 Artifact dispatch

`api/agents/dispatch.js` after the artifact row is patched to `status: 'delivered'`:

```js
const emailRes = await sendReadyEmail({
  email: profile.email,
  firstName: profile.first_name || '',
  agentSlug: registry.slug,
  artifactId: artifact.id,
});
emailAudit = emailRes.ok ? { ok: true, id: emailRes.id } : { ok: false, error: ... };
```

The audit object is folded into `artifact_runs.error` as a JSON block alongside any `missing_inputs` payload from the agent. So a successful artifact + failed email reads in the database as:

```json
{ "email": { "ok": false, "error": "address suppressed" } }
```

Email failure NEVER blocks the artifact delivery or the dispatch response. The artifact is still written, still readable in-app. The user does not receive an email. A bounced address logs the bounce reason for debugging without leaking it to the client.

For locked artifacts on free tier (Sensescape, Visual DNA, War Table), the email still fires. Per spec §11.3, the link goes to `/artifact?id=<id>`, the reading surface enforces the tier gate, and the paywall arrives at peak emotional moment.

## 6. Email-client compatibility notes

- **Inline styles everywhere.** Gmail, Outlook, and Apple Mail all strip `<style>` blocks. The lint warnings about inline styles in `/emails/*.html` are explicitly accepted; this is the email format, not the web format.
- **No web fonts.** Fraunces, Inter, JetBrains Mono are not loaded. Each font stack falls back to `Georgia, serif` for display, `Helvetica Neue, Arial, sans-serif` for body, `Courier New, Menlo, monospace` for mono. Email clients that strip web-font links would have rendered an unstyled fallback otherwise.
- **Box-shadow on the CTA pill.** Used for the hard offset shadow signature (`box-shadow: 0 6px 0 #2D1521`). Supported in Gmail web, Gmail iOS, Apple Mail. Outlook desktop ignores it; the pill falls back to a flat button with a 2 px ink border, which still reads as a button. Acceptable.
- **Dark mode.** A small `<style>` block with `@media (prefers-color-scheme: dark)` forces the cream background to stay cream in dark-mode clients that respect the preference. Gmail strips the block silently in clients that don't.
- **Hidden preheader.** A `display:none; max-height:0; overflow:hidden; font-size:1px;` div carries the preview text Gmail uses as the inbox-list snippet. Foundation-locked uses a fixed line. Artifact-ready uses the per-agent `preheader` variable.
- **`List-Unsubscribe` and `List-Unsubscribe-Post` headers.** Set on every send. Gmail uses these as positive signals for Primary tab placement. Both headers were verified present on the test sends (Resend forwards `headers` as the Resend SDK documents).
- **`X-Entity-Ref-ID`.** Distinct per template (`qb-foundation-locked` vs `qb-artifact-ready`). Helps Gmail thread reasoning. The deliverability test sends use a `-deliverability-test` suffix to keep test sends separate from production sends in Resend's dashboard.

## 8. Surprises and notes

### 8.1 Templates duplicated in two places

`/emails/*.html` and `/emails/*.txt` are the SOT for the preview harness. `api/_lib/email.js` carries the same strings inlined as JS template literals because Vercel Edge functions cannot read the filesystem at request time. Any change to a template requires editing both copies. A future improvement: a small build step that reads the `/emails/*` files and emits a JS module. Not in scope for Chapter 1; the duplication is two files, not twenty.

### 8.2 `lock-foundation.js` doc comment still references "dashboard"

The handler's top doc comment still has "...returns to the dashboard within 5 to 15 minutes." line. The user-facing email body now says "foundation" (correctly), but the function's internal documentation lags. Left alone for this step. A doc-only cleanup is a one-line fix that doesn't belong in a feature PR.

### 8.3 Resend's `last_event` is not the same as Gmail-tab placement

`last_event=delivered` means Resend got an SMTP 250 OK from Gmail's edge servers. It does NOT mean the email landed in Primary. Tab placement is a Gmail-internal decision that happens after the message is accepted. Confirmed visually by inspecting the recipient inbox; that's the only reliable measure.

### 8.4 Reply-to is the right address for this stage

`me@qtmbg.com` is the operator-personal address, not a routed alias. At Chapter 1 volume, every reply is read and responded to by Nizzar. When volume grows, swap in a `replies@quantumbranding.ai` alias that fans out. The helper accepts a `replyTo` parameter for that future change without touching the templates.

### 8.5 Welcome email (Signal Scan) was NOT migrated

`api/send-welcome-email.js` still has its own inlined HTML. Migrating it to use `api/_lib/email.js` is straightforward but out of scope for step 14 (the spec scope is foundation-locked + artifact-ready). Welcome email already lands in Primary and has been in production for weeks. No urgent reason to touch it.

### 8.6 No retry on the email send

If Resend returns 5xx, the dispatch path records the failure in `artifact_runs.error` and moves on. The artifact is still delivered. There is no retry queue. For Chapter 1, the tradeoff is correct: the artifact reading surface is reachable via the Foundation page anyway, so a missed email costs the user a notification, not access to the work. Email retry is a Chapter 10 concern.

### 8.7 The audit JSON is per-run, not per-artifact

`artifact_runs.error` carries the email audit for THIS run. If the artifact is regenerated (step 9's `POST /api/artifacts/[id]/regenerate`), a new run row records its own email audit. Historical email state is queryable per attempt rather than rolled up.
