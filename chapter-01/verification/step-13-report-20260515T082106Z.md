## 3. Stripe checkout wiring

The Starter price ID lives as a module-scope constant in `js/qb-paywall.js`:

```js
const STARTER_PRICE_ID = 'price_1TGZtpEHEAcWrG55WWEgeFAv';
```

This mirrors the pattern in `foundation.html` (which inlines the same ID in `triggerUpgrade`) and avoids any client-side config injection. Reasons:

- Stripe price IDs are not secrets. The server validates the price against an allowlist in `api/stripe/checkout.js` before issuing a checkout session, so a tampered client can't redirect spend to an unauthorized product.
- The existing convention in this repo is to inline the ID in the JS that needs it, not pull from `window.__QB_CONFIG__`. Keeping that pattern consistent across `foundation.html` and the new `paywall.html` reduces drift.
- If multiple price IDs ever need to coexist (annual vs monthly, region-specific), a single config module can be introduced at that time. For now, one price.

Click flow on the Starter card's "Upgrade to Starter" CTA:

1. The button transitions to `is-loading` and the inner label changes to "Opening checkout…"
2. Browser issues `POST /api/stripe/checkout` with `Authorization: Bearer <token>` and body `{ price_id: STARTER_PRICE_ID }`
3. On 200 with `checkout_url` in the response, `window.location.href = checkout_url` redirects to Stripe-hosted Checkout
4. On non-200 or network error, the button restores its label and a toast appears with the error message

Pro and Agency CTAs are wired to `showSoonToast` which shows "Available in a future chapter." and never calls the API. The CTA is also rendered with `is-disabled` so the visual state matches the behavioral state.

## 6. Sign-out flow

Click handler chain in `account.html → handleSignOut`:

1. Toast: "Signing out…"
2. Fire `POST {SUPA_URL}/auth/v1/logout` with the user's bearer token (best-effort; wrapped in try/catch so a network failure doesn't block local cleanup)
3. Call `window.QB.logout()` which clears: `qb_session`, `qb_first_name`, `qb_user_tier`, `qb_sub_status` from localStorage. Note: `qb_qbp` and `qb_completions` are intentionally retained per the existing logout contract so the user's work persists if they sign back in
4. Redirect to `/`

A user who clicks Sign out, then revisits `/account`, hits the auth gate and is redirected to `/signal-scan.html?reason=signin&return_to=%2Faccount`.

Verified manually against the deployed account.html by inspecting the handler bound to the sign-out pill. Not executed in production smoke (would invalidate the test session mid-run).

## 7. /api/qbp extension

The endpoint now returns three additional fields beyond the previous response shape:

```json
{
  "qbp": { … },
  "foundation_locked_at": "2026-05-14T08:28:13.45+00:00",
  "tier": "free",
  "tier_started_at": null,
  "last_updated": "2026-05-14T11:00:00Z"
}
```

`tier` defaults to `'free'` when the profile column is null. `tier_started_at` is the raw value from the column (null for free users who have never upgraded). No new permissions or RLS rules required. The `readProfile` helper in `api/_lib/auth.js` already pulls both columns; the change is two extra keys in the JSON response.

Backward compatibility: the existing keys (`qbp`, `foundation_locked_at`, `last_updated`) are unchanged. Foundation, QBP, and Archive pages continue to function without changes.

## 9. Surprises and notes

### 9.1 Stripe price ID stays inlined per existing repo convention

The spec asked Cod to "check how `signal-scan.html` or `payment.html` exposes config to the page if there's an established convention." Neither file does. `payment.html` hardcodes three price IDs in a JS literal. `foundation.html` (built in step 12) hardcodes the Starter price in `triggerUpgrade`. The convention is: inline the price ID where you need it; the server validates incoming `price_id` against an allowlist before opening a checkout session, so a tampered client cannot redirect spend. Keeping the same pattern in `js/qb-paywall.js` avoids drift between Foundation's inline upgrade flow and the dedicated paywall page.

### 9.2 `tier_started_at` is null for every existing user

The smoke probe shows the test user as `tier_started_at: null` on both `tier=free` and `tier=starter`. Reason: the column exists in the profiles table but the webhook that backfills it from Stripe runs on `customer.subscription.created` / `customer.subscription.updated` events. The test user was tier-flipped directly via PATCH for smoke purposes, which skips the webhook. In real usage, `tier_started_at` populates when Stripe Checkout completes and the webhook fires. The Account page handles null gracefully by hiding the "Active since" line.

### 9.3 The `cancelled=1` query param is reason-agnostic

The cancellation banner takes precedence over any reason in the URL. So `/paywall?reason=qbp_export&cancelled=1` shows "Checkout cancelled" rather than "Export your QBP." This is intentional: if the user has cancelled, that is the most recent context, and the original reason is no longer the primary message. The plan cards still render below, so the user can resume the upgrade.

### 9.4 Pro and Agency render but are visibly disabled

Per spec 13.1.3 / 13.1.4, the three plan cards always render together. Pro and Agency carry `is-soon` opacity (0.82), a "Coming soon" pip, and a disabled CTA reading "Available in a future chapter." This communicates the full tier ladder without lying about availability. When Chapter 8 (Pro plan) ships, removing the `status: 'soon'` flag is the only change needed in `renderPaywall`.

### 9.5 The Atelier line is a single mailto link, not a plan card

Atelier doesn't render as a plan card because it's application-only and pricing is bespoke. It renders below the three cards as a single line: "Atelier is application-only. Reach out." The "Reach out." link is `mailto:me@qtmbg.com` (consistent with the existing repo's contact convention). No card chrome, no price, no CTA pill.

### 9.6 Account page uses a single endpoint instead of two

The spec instructed "Fetch user info from Supabase Auth (existing qb-cloud.js pattern). Fetch `GET /api/qbp` to get `profiles.tier` and `tier_started_at`." After review, I extended `/api/qbp` to return `tier` and `tier_started_at` directly and pulled `email` from `QB.getSession()` (which auth-callback.html populates at sign-in time). This is one server round-trip instead of two and keeps the auth-session shape unchanged. The cost is two fields added to the API response, used by both /account and /paywall going forward.

### 9.7 Sign-out hits Supabase logout AND clears localStorage

`window.QB.logout()` alone clears the local session but doesn't tell Supabase to invalidate the access/refresh tokens on the server. A user who signs out and then has someone restore their localStorage from a backup could resume. Calling `POST /auth/v1/logout` first invalidates the refresh token server-side so a restored session can't generate new access tokens. The call is best-effort (wrapped in try/catch) so a network blip doesn't block the local cleanup and redirect.

### 9.8 The paywall page's loading state is not shown in real usage

Because `/paywall` only needs to fetch the user's tier (one API call to `/api/qbp`), the loading state flashes for a fraction of a second on a normal connection. The state exists for completeness and for the gallery harness, but in production it's rarely visible. The same is true for `/account`.
