### 2.1 Restricted markdown parser

Inline, no external lib. Three rules total:

```
\n\n           → <p> boundary
**bold**       → <strong>
*italic*       → <em>
```

Everything else is HTML-escaped before parsing. Headings, lists, images, links, raw HTML — all rejected at parse time. The schema validator enforces the same constraints at write time; the renderer's parser is defense in depth.

## 4. Positioning map — rendering approach (the trickiest one)

The map renders as inline SVG with a `viewBox="0 0 100 100"` so positioning is numeric and the chart scales with the container. The container itself is a 1:1 aspect-ratio div, full-width on mobile, capped via `max-width` on desktop.

**Coordinate mapping:**
- `x` (0–1, low→high left→right) maps to SVG `cx = x * 100`
- `y` (0–1, low→high bottom→top per spec §7.2) maps to SVG `cy = (1 - y) * 100` — inverted because SVG y grows downward

**Visual treatment:**
- Background fill: `--cream`
- Cross-hair axes: dashed `--ink-25` at 50/50 for orientation
- Regular placement dot: `r=1.8`, fill `--ink-50`, stroke `--ink`
- `is_self` placement dot: `r=3.4`, fill `--rose`, stroke `--rose-deep`
- Label: SVG `<text>` element placed below the dot. `text-anchor` switches between `start` / `middle` / `end` based on the dot's x position so labels stay in-frame at the edges. Label font is loaded by the page's font stack (Inter); the SVG only inherits the family.

**Axis labels:**
- Surrounding the SVG in DOM (not SVG) so they wrap naturally with CSS.
- Top: `y_axis.high` centered above the chart.
- Bottom-left: `x_axis.low`.
- Bottom-right: `x_axis.high`.
- Left: `y_axis.low` rotated `vertical-rl` + `rotate(180deg)` so it reads bottom-to-top.

**Why SVG over absolute-positioned divs:** SVG keeps the chart's geometry intact across resizes, supports `preserveAspectRatio="xMidYMid meet"` for clean centering, and renders crisp at any zoom level. Absolute-positioned dots would have required JS to recompute on resize and lose semantic structure for screen readers. The SVG's `aria-label` describes the axes in one phrase.

## 5. Illustration tinting

Spec §12.5 mandates CSS filter tinting on body-section illustrations to bring the editorial PNGs into the v3.2 cream/gold register.

**Filter chosen:** `sepia(0.35) saturate(1.15) hue-rotate(-8deg) brightness(0.98) contrast(1.02)`

Rationale: modest, preserves the original character of the PNGs (which are mostly already in a warm earth-tone register). The spec's `sepia(1) saturate(2) hue-rotate(330deg)` template would have washed out the originals. The chosen filter shifts warmth without flattening tonal range.

**Dropping fallback:** the spec authorized dropping illustrations rather than ship with palette drift. The filter ships **enabled**. If any specific slot reads poorly in a downstream surface, that slot's body section can omit `illustration_slot` at the content layer and the renderer will gracefully render no figure.

**Inventory enforcement:** `buildIllustration(slot)` validates the slot against `ILLUSTRATION_INVENTORY` from the schema validator. Unknown slugs render nothing (no broken image, no error). Step 5/6 fixtures use no illustrations (`illustration_slots_used: (none)` across all four production artifacts), so the illustration path is exercised only by the Soul Map fixture for now.

## 8. Surprises and notes

### 8.1 Soul Map artifact_id drift

The smoke test found the most recent Soul Map row at `8617d462-fc76-4430-92d8-923b25b370b3` (version 3), not the `4316d9d4-...` row noted in steps 2–3. A new version was created when the step-7 test script's `POST /api/artifacts/<id>/regenerate` assertion fired against the dispatch endpoint. Production behavior is correct — the versioning chain works, parent_artifact_id links versions, and the API surfaces the highest-version delivered row first.

### 8.2 No illustrations in the wild yet

None of the four production artifacts include an `illustration_slot`. The current agent prompts (Soul Map / Sensescape / Visual DNA / War Table) do not request illustration assignment; they leave that to the editorial surface's defaults. The renderer's illustration code path is exercised only by the Soul Map fixture (which includes `blank-slate` and `doubter` slots). This is by design for Chapter 1 — illustrations on artifacts can be added in a Chapter 2 polish pass once the agent framework refactor exposes a clean way to assign them.

### 8.3 SVG positioning_map labels

Inline SVG `<text>` does not wrap. Labels longer than ~28 characters will overflow the chart frame. War Table's production labels (`"Harley-Davidson"`, `"Patagonia"`, `"Hero Archetype"`, `"Your Brand"`) all fit comfortably. For longer labels the prompt would need to trim at the agent layer — flagged as known debt for any agent that places competitors with verbose names.

### 8.4 Auth redirect path

`artifact.html` redirects unauthenticated users to `/signal-scan.html?reason=signin&return_to=<encoded /artifact?id=...>`. This matches the magic-link redirect pattern set in step 1 (PR #20), so the user returns to the right artifact after sign-in.

### 8.5 Share controls download path

The "Download PDF" button in the share controls calls `/api/qbp/export`, which per the step-7 deferral still returns a JSON file (PDF generation deferred to a Chapter 1 polish pass). On the artifact reading surface this is acceptable transitional behavior — the user gets their QBP as JSON. A future polish pass can switch the endpoint to PDF without changing the renderer.

### 8.6 "Loading skeleton paint cost"

The IDE flagged that the skeleton's `background-position` animation triggers Paint each frame. The skeleton displays for under a second during fetch; cost is negligible in practice. A polish pass could replace the gradient sweep with a transform-only overlay if profiling ever shows it matters.

### 8.7 Renderer is pure

`renderArtifact` is a pure function of `(container, content, opts)`. There is no module-level mutable state in the renderer. Re-running with the same inputs is idempotent. The page-level state machine in `artifact.html` calls the renderer once per fetch outcome.
